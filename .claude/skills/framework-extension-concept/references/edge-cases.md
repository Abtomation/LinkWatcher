# Edge cases — Framework Extension (PF-TSK-026)

Consult-on-stumble record for the Framework Extension task and this skill (PF-PRO-059
two-zone convention). Each entry is keyed to the situation in which it applies — read the
entry whose situation you are in; nothing here is part of the routine path. Entries are
appended or rewritten per the workspace Standing Orders (an entry names its provenance; the
~150-line promotion tripwire applies).

## The initiating directive already fixed the concept's direction

**Situation**: at the concept-direction checkpoint (Step 3), the human's initiating
instruction already fixed the extension's direction and scope — a go/no-go would re-ask what
the directive answered.

Record the directive as the Step 3 approval instead of re-presenting, and state that
interpretation explicitly when the written concept is next presented (Step 5, or earlier on
any open direction question) so the human can veto a misread. This satisfies the checkpoint's
function — a go/no-go before investing in the deeper impact analysis — it does not skip it:
any direction question Step 1 surfaced still goes to the human before full authoring, per the
step's own raise-it-early rule. (Provenance: PF-FEE-1708, absorbed by PF-IMP-1901.)

## A work item targets a file outside the workspace

**Situation**: planning — or executing, when the block surfaces as a denied edit mid-phase —
a component whose home lies outside the workspace's writable tree: an owner-held file such as
the owner's user-level configuration, where agent edits are blocked by tooling permissions.

Plan (or re-plan) the item as a **drafted-text-for-owner deliverable**: the session produces
the finished text and hands it to the owner; placement stays with the owner, and the roadmap
marks the item complete on handover, not on placement. Kin to Step 19's
never-edit-a-project's-working-tree rule — the same boundary, a different target tree.
(Provenance: PF-FEE-1709, absorbed by PF-IMP-1901.)
