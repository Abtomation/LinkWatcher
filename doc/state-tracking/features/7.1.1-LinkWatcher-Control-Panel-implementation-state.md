## 1. Feature Overview

### Feature Description

The LinkWatcher Control Panel is the project's **first GUI surface**: a single-window Tkinter/ttk desktop application that acts as a *pure supervisor* over the LinkWatcher daemons running across every registered project. LinkWatcher daemons run silently in the background, one per project, started automatically by a Claude `SessionStart` hook. Today an operator has no unified way to see what is running, stop a daemon, read its log, edit its configuration, or run a validation scan — they must inspect OS process lists and open log/config files by hand.

The panel provides one desktop window to see and control all daemons across projects: list them with live status, start/stop them, tail their logs, view/edit each project's configuration, trigger link validation, and drain-then-terminate all managed daemons when the window closes. The window also surfaces itself automatically whenever a daemon is auto-started by the hook, so the operator always has a visible handle on LinkWatcher activity.

Architecturally, the panel introduces **no new daemon-side contract**. It manages daemons entirely through existing external surfaces — the lock file, OS process state, the launcher script, the `--validate` CLI mode, log files, and the per-project YAML config — which keeps it decoupled from the daemon and crash-safe (panel failure never harms a running daemon).

### Business Value

- **User Need**: Manage link maintenance across multiple projects from one window, without hunting through process lists and log files.
- **Business Goal**: Make LinkWatcher activity visible and controllable; pair every hook-started daemon with a visible operator handle.
- **Success Metrics**: An operator can identify and control every running daemon from one window; panel-initiated shutdown produces zero corrupted files; start/stop/log/validate/config-edit are all achievable without the command line.

### Scope

**In Scope**:

- Live daemon list across all registered projects with truthful status (running / stopped / stale-lock / starting / draining / force-stopped)
- Start (via the existing launcher) and stop (drain-then-terminate) of individual daemons
- State sync with reality (daemons started/stopped outside the panel, e.g. by the hook)
- Live log tailing, on-demand link validation, and per-project config view/edit with validate-on-save
- Drain-then-terminate-all on window close, bounded by a grace period (can never hang)
- Single-instance behavior + hook auto-open/surface of the one window
- Installer + hook-wrapper changes to ship and auto-open the panel

**Out of Scope**:

- A cooperative graceful-stop contract (**stop-sentinel** a daemon polls) — deferred; MVP uses bounded drain-then-force-terminate
- Any new API/daemon-side contract, and any database/schema
- Automatic daemon start-up ownership (the `SessionStart` hook remains the automatic start path)
- Performance tests and full E2E acceptance (routed to their own downstream tasks)

### Decision 2: Add a `.framework-central-pointer` discovery tier to the registry resolution chain

**Date**: 2026-07-27 (Core Logic Implementation, Phase A)
**Context**: TDD §4.1 specified a three-source registry chain (`--registry` → env → `panel-config.yaml` key → error banner). Out of the box — a hook-auto-opened panel with no config — that lands on the error banner, a poor first-run experience for a tool meant to auto-open and "just show your daemons."

**Options Considered**:

1. Keep the TDD's three-source chain - Pros: matches the TDD verbatim. Cons: zero-config launch shows an error banner; forces the operator to configure a path the framework already knows how to find.
2. Add pointer-based discovery as a fourth tier before the error - Pros: reuses the framework's canonical "where is central?" locator (`.framework-central-pointer`) → no second source of truth; the hook (which knows its project) passes `--project-root` and a manual launch from inside a project is found by a cwd walk-up, so both common paths become zero-config. Cons: small deviation from the TDD; the panel reads a framework-infra file (but it already reads the central registry — same layer).
3. Bake the resolved central path into a shipped `panel-config.yaml` at install time - Pros: context-independent at runtime. Cons: records central's location in a *second* place that can drift from the pointer.

**Decision Made**: Option 2 — checkpoint-approved 2026-07-27.

**Rationale**: One source of truth for central's location; zero-config for both the hook-auto-open and manual-from-project paths; the error banner remains only for the genuinely unconfigured case. The three explicit sources still outrank it, so nothing that worked before changes.

**Implications**: TDD §4.1 resolution order updated. The hook wrapper will pass `--project-root` (Phase F); until then the cwd walk-up covers manual launches. Pointer discovery counts only when the derived registry file exists (a phantom path falls through to the error state). Covered by the UNIT-S4 pointer-tier tests.

### Decision 3: Give the panel diagnostic log its own module (`panel_log.py`)

**Date**: 2026-07-27 (Core Logic Implementation, Phase A)
**Context**: The TDD (§3.3) mandates a panel log (`<install>/logs/panel.log`) but its §9 module list does not enumerate a module for it. The log is written by many modules (discovery, lifecycle, validation, config_edit, app).

**Decision Made**: A dedicated `panel_log.py` exposing `setup_panel_log()` / `get_panel_logger()`.

**Rationale**: A shared logger obtained from a dedicated module lets every worker module call `get_panel_logger()` without importing `app.py` (which imports *them*) — avoiding an import cycle. Centralizing the setup keeps it testable and idempotent, and console-less-safe (guards `sys.stderr is None` under `pythonw`).

**Implications**: One module beyond the TDD §9 list (a minor structural addition, not a behavior change).

### Decision 4: Identity matches the normalized `--project-root` *value*, not a command-line substring

**Date**: 2026-07-31 (Core Logic Implementation, Phase B)
**Context**: TDD §4.4 specified the three-way identity test as "command line contains `main.py` **and** the project root" — the same literal-substring rule the launcher's `Test-LinkWatcherAlreadyRunning` uses. Inspecting the actually-running daemons showed the registry stores `C:\Users\...\LinkWatcher` while the live daemon's command line carries `c:\Users\...\LinkWatcher` (lowercase drive letter, supplied by the hook's cwd).

**Options Considered**:

1. Implement the rule literally - Pros: matches the TDD text and the launcher verbatim. Cons: **demonstrably broken today** — LinkWatcher's own running daemon classifies as STALE_LOCK, and Phase C's Stop would refuse to act on it. Also admits a false positive: root `C:\proj\App` substring-matches a daemon for `C:\proj\AppExtra`, i.e. a wrong-process termination target.
2. Extract the `--project-root` argument value and compare it normalized (case-fold + separator normalization) - Pros: fixes both defects; strictly stronger than substring matching; still exactly the three-way agreement D-T5 requires. Cons: small deviation from the TDD wording; a process with no `--project-root` in its command line becomes unidentifiable.
3. Normalize but keep substring containment as a fallback - Pros: tolerant of unusual command lines. Cons: reintroduces the prefix false positive — the one failure mode with the worst consequence.

**Decision Made**: Option 2 — checkpoint-approved 2026-07-31.

**Rationale**: The TDD's *intent* (D-T5: never act on the wrong process) is served by Option 2 and actively defeated by Option 1. Comparing the parsed argument value is both more permissive where it should be (case) and stricter where it must be (prefixes).

**Implications**: A daemon started without `--project-root` (the flag defaults to the working directory, invisible in the command line) is never claimed by any project — the conservative choice, since an unattributable process must never be terminated. TDD §4.4 step 2 and D-T5 updated. Covered by three dedicated guard tests plus the `extract_project_root` parametrization.

### Decision 5: A live daemon outranks a stale lock in classification

**Date**: 2026-07-31 (Core Logic Implementation, Phase B)
**Context**: The TDD §4.4 matrix reads lock-first: "lock exists but PID dead/mismatched → STALE_LOCK". It does not say what to do when a stale lock coexists with a daemon that the command-line scan *does* find — a real combination (a reclaimed or orphaned lock alongside a running daemon).

**Decision Made**: Classify RUNNING, with the stale lock surfaced in the row's detail note. STALE_LOCK is reserved for a lock with genuinely nothing behind it.

**Rationale**: The process table is truth; the lock is diagnostic. Rendering a *running* daemon as not-running would leave it unstoppable from its only supervisor — the exact blindness the feature exists to remove. EC-1/EC-3 are unaffected: a lock with no live daemon is still STALE_LOCK with empty `pids`, so nothing can be acted on.

**Implications**: TDD §4.4 step 4 rewritten as an explicit precedence list. Also resolved there: a registered project whose root is missing from disk is STOPPED with a "project root not found" detail, rather than a new `DaemonStatus` member or a silently dropped row.

### Decision 7: Termination acts on every kill-time-matching process, not `resolve_pair` from the lock anchor

**Date**: 2026-08-10 (Core Logic Implementation, Phase C)
**Context**: TDD §4.4 says every lifecycle operation "acts on the pair", and the Phase B handoff suggested reusing `resolve_pair` at kill time. Implementing the kill-time guard showed a simpler rule with strictly better properties.

**Options Considered**:

1. Re-anchor on the poll-time lock PID and expand via `resolve_pair` - Pros: matches the handoff note literally. Cons: depends on poll-time data the guard exists to distrust; misses accidental duplicate daemons for the same project (they are outside the anchored pair but equally this project's daemons).
2. Terminate the full set of processes passing `is_daemon_for` at kill time - Pros: the guard *is* the target selection — one rule, fresh snapshot, nothing unidentified ever touched; the verified pair is this set by construction, and accidental duplicates (the PF-IMP-967 condition) are cleaned up too. Cons: none found — the set is always a superset of the pair and every member independently passes three-way identity.

**Decision Made**: Option 2 — presented at the Phase C scope checkpoint (approved 2026-08-10) and recorded here.

**Implications**: `resolve_pair` remains discovery-only (classification/uptime). UNIT-L8/L9 assert the pair-and-nothing-else and refusal properties. Three further implementation choices from the same checkpoint: launcher output captured via **temp files, never pipes** (the spawned daemon inherits handles and a pipe-capturing parent hangs — launcher header / TE-E2E-009); start-failure reason falls back from stderr to the launcher's stdout error lines (`Write-Host` lands on stdout); outcome pins (FORCE_STOPPED / START_FAILED) carry a **30 s TTL** before poll truth wins again.

### Decision 8: Shutdown completion is observational — the poller runs through shutdown

**Date**: 2026-08-10 (Core Logic Implementation, Phase D)
**Context**: The shutdown dialog must truthfully flip rows to "✔ Stopped", and the app must exit exactly when every target is resolved. A clean drain leaves its DRAINING pin for the poll to resolve (Phase C design), so something must still be observing reality during shutdown.

**Options Considered**:

1. Keep the poller running until actual exit; the orchestrator subscribes to the model and completes when every target leaves the still-draining set - Pros: one truth mechanism end to end — the same observation loop that makes the panel truthful also decides the exit; no second completion signal to reconcile. Cons: exit lags the last drain by up to one poll interval (≤ 2.5 s).
2. Have shutdown workers post explicit terminal outcomes and stop the poller at close - Pros: exit fires the instant the last worker returns. Cons: invents a shutdown-only completion channel that bypasses the reconciliation rule; rendered state and exit condition can then disagree with reality (the exact failure mode the model design exists to prevent).

**Decision Made**: Option 1, with a **watchdog backstop** at grace + 15 s (exit-wait 10 s + slack) that forces completion regardless of worker state — checkpoint-approved 2026-08-10.

**Rationale**: AC-9 is served by bounds, not by speed: every drain is internally bounded, the watchdog bounds the pathological case, and the ≤ 2.5 s observation lag is irrelevant next to the 3–20 s drain itself. Truthfulness stays a single mechanism.

**Implications**: `STILL_DRAINING_STATUSES` is defined once in `lifecycle.py` and shared by the orchestrator and the COMP-5 rendering rules, so the dialog and the exit condition can never count "resolved" differently. Rows already DRAINING from a user stop are adopted as targets (busy guard rejects the duplicate dispatch). A STARTING row at close time is **not** drained — recorded as a Known Limitation (§10). Verified live: close-with-running-daemon exited by itself 4.9 s after close.

### Decision 9: Validation count from the report file; config validated via `from_file` on the save temp

**Date**: 2026-08-10 (UI Implementation, Phase E)
**Context**: Two open implementation choices landed at the Phase E checkpoint: how to extract the broken-link count (TDD §8 Q3 — stdout summary vs. report file), and where exactly the config save pipeline should run the real validator.

**Decision Made** (checkpoint-approved 2026-08-10):

1. **Q3**: the report *path* is parsed from stdout's ANSI-stripped `Report written to <path>` line (falling back to the conventional `logs/linkwatcher/LinkWatcherBrokenLinks.txt`); the *count* comes from the report file's stable, colorless `Broken links  : N` line (falling back to the same line in stdout). 2. **Config save**: `yaml.safe_load` first (line-numbered errors + top-level-mapping check), then the candidate bytes are written to a same-directory temp file and constructed via the real `LinkWatcherConfig.from_file()` + `validate()` **on that temp file** — the exact bytes to be persisted go through the exact code path the daemon uses at startup (D-T6 extended to the parse itself) — then `os.replace`. An empty/comments-only config is valid by the documented "empty means defaults" contract.

**Implications / companion details from the same checkpoint**: `LogTail` normalizes CRLF with a held-back `\r` (daemon logs are text-mode `\r\n`; a pair split across reads must not leak); per-tick reads are capped at 64 KB (UI-thread guard); rotation reattach also fires when a *newer* `LinkWatcherLog*.txt` sibling appears while the current file is quiet (strictly stronger than the TDD's "missing or shrank" wording, aligned with the drain watcher's newest-by-mtime rule); scroll-lock is spec-literal (only the checkbox or Ctrl+End resume following); the three pane views live inside the TDD-listed `views/` package (Decision 6 precedent). Toolbar accelerators (Alt+S/Alt+T/F5) from PD-UIX-003 §4.2 were observed unwired (Phase C code) — deferred to Phase G hardening.

### Decision 10: A banner handshake proves the peer is a panel; the simultaneous-launch race is accepted

**Date**: 2026-08-10 (Integration & Testing, Phase F)
**Context**: TDD §4.5 specifies "a second launch reads the port file, connects, sends `SURFACE`, and exits; connect failure ⇒ stale port file ⇒ the new launch takes over." Implementing it surfaced two gaps the wording leaves open.

**(a) A bare successful connect is not proof of a panel.** Ephemeral ports are recycled, so a stale `panel.port` can name a port some unrelated process now owns. Under the literal rule that connect succeeds, the launch reports "already running" and **the panel never opens again** until the file is deleted by hand.

**Options Considered**:

1. Implement literally - Pros: matches the TDD text. Cons: a recycled port permanently blocks the panel — a silent, self-inflicted denial of the whole feature.
2. Require a one-line ack (`SURFACE\n` → `LINKWATCHER-PANEL OK\n`) before believing an incumbent exists - Pros: makes "connect failure ⇒ stale" actually trustworthy, which is what the TDD wanted; still a fixed one-verb protocol with no data surface. Cons: two bytes of protocol beyond the TDD wording.

**Decision Made**: Option 2 — the handshake *is* the stale-detection mechanism the TDD assumed connect alone provided. Covered by a dedicated test that stands up a foreign listener on the published port and asserts the panel still opens.

**(b) Simultaneous launches can both win.** Read → connect-fail → bind → publish is not atomic, so two launches within the same few milliseconds both fail to connect, both bind different ephemeral ports, and both publish; the later writer owns the file and the other panel becomes unreachable (it stabilizes at exactly two windows, never more). **Accepted as a Known Limitation** (checkpoint-approved 2026-08-10) rather than adding a second exclusion primitive: the window is sub-millisecond, both windows are visible to the operator, and EC-9's actual harm — conflicting start/stop — requires the operator to drive both. A lock-file/named-mutex alternative would put two mechanisms in play that must agree about who is the instance.

**Implications**: `PANEL_BANNER` is part of the module's contract. Bind failure is **fail-open** (a panel with no single-instance protection beats no panel), and `release()` deletes `panel.port` only when it still holds this instance's port — the same self-owned-resource rule the daemon applies to `.linkwatcher.lock`.

### Decision 11: Phase G hardening — three changes

**Date**: 2026-08-10 (Integration & Testing, Phase G)
**Context**: The hardening pass had to make two surfaces testable that the "no widget instantiation" rule had left unreachable, and had to close the accelerator gap carried over from Phase E.

**(a) The dispatcher drain moved to a module-level `drain_queue(queue, log)`.** INT-8 covers "any worker"; the UI-thread half of the isolation rule lived inside `ControlPanelApp._pump_dispatch_queue`, and the class builds a `Tk()` in `__init__`, so the test spec's "Tk display: avoided" rule made it unreachable. The drain is now a pure function the pump calls — the same display-free seam the rendering rules use (Decision 6). Behavior is unchanged; the extraction is what makes the rule assertable.

**(b) A pending discovery is no longer rendered as an empty registry.** Found by the Phase G live smoke run, not by any test: the first `psutil` pass on this machine took **7.5 s** for 409 processes (subsequent passes 0.11 s), and for that whole window the list pane asserted *"No registered projects found."* while the status bar said *"0 daemons running"*. Both are claims about reality the panel had not yet observed — the same falsehood the truthful-state rule forbids for row status (TDD §4.3), in the pessimistic direction. `list_pane_display` gained a fourth mode (`loading` → "Discovering daemons…"), selected while `model.last_refresh is None`; a real error still outranks it, so an unresolved registry never sits on a spinner forever. The cold-start cost itself is not a defect (steady-state polls are well inside the §7.1 budget) and is handed to Performance & E2E Test Scoping, which owns per-feature performance tests.

**(c) Toolbar accelerators route through button enablement.** `Alt+S`/`Alt+T`/`F5` fire their handler only when that button is enabled, so the COMP-1 matrix governs the keyboard exactly as it governs the mouse — a keystroke can never trigger an action the UI shows as unavailable.

### Implementation Patterns Used

**State Management Pattern**:

- Pattern: Single observable model (`AppModel`) with one-way data flow; worker threads → thread-safe queue → UI-thread dispatcher (`root.after`)
- Why: keeps Tk single-threaded and the rendered state truthful (poll-observed or deadline-bounded pin)
- Where: `model.py`, `app.py`, `discovery.py`, `views/`

**Error Handling Pattern**:

- Pattern: per-surface pane-local error states; worker exceptions caught, logged to the panel log, rendered — never propagated to the mainloop
- Why: one project's/one surface's failure never takes down the panel or other rows
- Where: every external-surface module (`discovery`, `lifecycle`, `validation`, `config_edit`, `log_tail`)

**Data Flow Pattern**:

- Pattern: external reality (registry + locks + psutil + logs) → poller → queue → model → views; user actions dispatch operations whose observed results update the model
- Why: views render from the model only; actions never mutate widget state directly
- Where: the full poll cycle and every user action (TDD §4.3)

### Decision 12: Registry resolution is workspace-shaped — own child registry, then the parent hop

**Date**: 2026-08-28 (Bug Fixing, PD-BUG-148)
**Context**: Decision 2 added pointer discovery and described it as reusing "the framework's canonical
'where is central?' locator". It did not reuse that locator; it hardcoded a *snapshot* of one instance
of it — face at `process-framework/`, registry at `process-framework-central/project-registry.json`
indexed by `projects`. The locator later became role-derived, and the snapshot went stale. Measured
2026-08-28 with an isolated cwd (only `--project-root` exercised, as the hook passes it): the
framework-builder, and both framework-role workspaces, resolved to nothing; only a leaf project
resolved. Zero-config discovery worked **only at leaf workspaces**.

**Root cause — two independent mechanisms**: (1) the face is not always `process-framework/` (a
self-hosted producer declares `blueprint/process-framework`), so the pointer file was never found
there; (2) a parent-pointer names the **parent**, so joining `process-framework-central/project-registry.json`
to it yields the *parent's* central — right for a leaf, whose supervisor list genuinely lives in its
parent, but wrong for every non-leaf, and the parent's registry need not be a project registry at all.
Mechanism (2) is why the framework-role workspaces failed; the bug report identified only (1).

**Options Considered**:
1. Derive the registry shape from the workspace's declared `role` (a role→filename/key table mirroring
   the framework's own resolver) - Pros: faithful to the framework contract. Cons: encodes that contract's
   taxonomy in LinkWatcher, so a new role breaks the panel again; measured to fail identically on the
   blueprint case, so it bought nothing there.
2. Look for a child registry where child registries live, and fall back to the parent hop - Pros: no role
   table, no taxonomy; strictly less framework knowledge than before. Cons: still infers a layout LinkWatcher
   does not own.
3. Per-workspace configuration naming the registry - Pros: immune to framework change. Cons: abandons
   zero-config for every workspace including the one that works today; duplicates a location the framework
   already knows, with a staleness failure mode; a panel-only key in the daemon's config schema also logs an
   "unknown configuration key" warning on every daemon start.

**Decision Made**: Option 2 — human-approved 2026-08-28, as an interim ahead of the structural fix below.

**Rationale**: It removes framework knowledge rather than adding it, and it is the smallest change that
makes every workspace shape resolve. Verified against five real workspaces; the leaf path returns a
byte-identical result to the pre-fix behaviour, so the one path that worked is provably unchanged.

**Two deliberate constraints**:
- **Own-registry lookup takes the workspace root exactly, and never walks up.** A cwd walk-up would adopt
  a registry it merely walked past: a producer's blueprint tree carries a **zero-row seed** registry, and
  resolving to it renders the calm EC-8 "no registered projects" state — a wrong answer that reads as a
  valid one, which for a monitoring tool is worse than an error banner. Pinned by
  `test_cwd_walkup_does_not_claim_an_ancestors_own_registry` and, for the real blueprint shape (seed *and*
  pointer both present), `test_walkup_past_a_seed_registry_prefers_the_pointer`.
  **Amended 2026-08-28 (Code Review CR-1, human-approved):** the root was originally confined to an
  *explicit* `--project-root`, which made the tier unreachable in practice — the launchers forward their
  arguments and add none, so every manual launch fell through to the parent hop and a non-leaf workspace
  silently got the wrong list (measured at appdev: own 4 projects vs. parent 3 frameworks, with nothing in
  the UI distinguishing them). The current directory is now accepted as an *implied* root. The no-walk-up
  half of the constraint is unchanged and is what still keeps the seed out of reach; standing one directory
  below a seed-carrying tree resolves through the pointer, pinned by
  `test_implied_root_is_the_cwd_itself_and_is_never_walked_up`.
- **The face is read, not assumed** — `paths.process_framework` from `doc/project-config.json`, falling back
  to `process-framework/`. Pinned at the resolution level by
  `test_declared_face_is_read_when_following_the_parent_pointer` (added for CR-4; face handling was
  previously covered only through `launcher_path`).

**Scope added during the fix (Step 20 sweep)**: `lifecycle.launcher_path` carried the *same* hardcoded face
assumption, so Start would have failed for a workspace whose face is elsewhere. That defect was latent only
because such a workspace could never be listed — this fix made it reachable, so shipping the resolution half
alone would have delivered a panel that lists a workspace and then cannot start it. Both now resolve through
one shared `workspace_face_dir` helper, removing the duplicated assumption.

**Known residual (accepted)**: this remains *inference of a layout LinkWatcher does not own*, which is the
category that produced the bug. Industry practice for multi-instance supervisors is self-registration into a
tool-owned runtime directory (Watchman's `watch-list`, Gradle's `~/.gradle/daemon`) rather than reading a
third party's inventory — and the registry answers "who receives rollouts", never "where daemons run", so it
structurally cannot list an unregistered workspace that is running one. Filed as a feature request; see the
Issues & Resolutions Log entry for PD-BUG-148.

**Implications**: TDD §4.1 resolution order and its constraint bullet updated (tiers 4-6);
Control Panel Reference resolution table, `--project-root` description and the per-project launcher path

**2026-08-25 (Bug Fixing, PF-TSK-007) — PD-BUG-137: a panel-initiated stop left a stale
`.linkwatcher.lock` behind.** `cleanup_lock` made exactly one `unlink()` attempt and swallowed any
`OSError` into a bare `False`. Windows cannot unlink a file another handle holds open without
`FILE_SHARE_DELETE`, so that single attempt loses to any concurrent holder — and `False` was
returned for five distinct conditions (no lock, unreadable, foreign lock, wrong PID, unlink failure),
so `lock_removed=False` in the panel log carried no information about which had occurred.

**The evidence pointed at a race, and the triage read it as a branch.** The filed report contains the
discriminator: the explicit per-row stop at 13:50 removed the lock (`lock_removed=True`) while the
window-close stop at 14:10 did not — same function, same project, no structural difference between
those paths. Two reproductions confirmed the drain itself is sound: a single-process daemon and the
real venv-shim pair (lock holding the child PID, exactly the failing shape) both cleaned up, at
3.47 s against the incident's 3.36 s. What the probes lacked is what the panel always has — a poller
reading every project's lock each cycle and continuing throughout shutdown. Isolating that:
**208/300 unlinks failed with `PermissionError: [WinError 32]` under a concurrent reader.**

**Scope honesty.** The poller is a *confirmed* holder, not necessarily *the* holder in the original
incident: it reads for well under a millisecond every 2.5 s, so a collision with the single instant
of the unlink is rare, and the triage's "Frequency High" was an inference from one observation rather
than a measurement. An antivirus scan of a just-terminated process's files fits a recurring failure
better. The fix does not depend on knowing which: the backoff addresses the whole class, and the new
warning names the actual holder's error next time.

**Fix.** Escalating backoff (0.05/0.1/0.2/0.3/0.4 s, ~1.05 s total, six attempts) around the unlink;

and still undeletable now emits `lock_cleanup_failed` naming the path, owner PID, attempt count and
