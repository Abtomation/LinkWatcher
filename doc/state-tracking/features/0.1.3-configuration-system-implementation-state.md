## 1. Feature Overview

### Feature Description

The Configuration System provides multi-source configuration loading, validation, and environment preset management for LinkWatcher. The system supports loading configuration from YAML files, JSON files, environment variables, and CLI arguments, with a defined precedence order (CLI > env > file > defaults).

The core class `LinkWatcherConfig` (`config/settings.py`) holds all configuration values as a dataclass with typed fields and default values — the single source of truth for the default schema (PD-BUG-103: `defaults.py` previously re-declared the default sets and silently diverged). The `defaults.py` module instantiates `DEFAULT_CONFIG = LinkWatcherConfig()` from those defaults, and the `config/__init__.py` re-exports the public API. Three environment presets (development, production, testing) provide pre-configured profiles optimized for different usage scenarios.

A `validate()` method ensures configuration consistency, checking for invalid combinations, missing required paths, and type correctness. Configuration examples in `config-examples/` demonstrate common setups.

### Business Value

- **User Need**: Different environments (development, CI, production) require different monitoring behavior — file filters, logging levels, dry-run settings, etc.
- **Business Goal**: Zero-code configuration changes via files, environment variables, or CLI flags.
- **Success Metrics**: Configuration loads correctly from all sources; validation catches invalid combinations before service startup.

### Scope

**In Scope**:

- `LinkWatcherConfig` dataclass with typed fields and defaults
- Multi-source loading: YAML, JSON, environment variables, CLI arguments
- Precedence order: CLI > environment variables > config file > defaults
- 3 environment presets: development, production, testing
- `validate()` method for configuration consistency checking
- Example configuration files

**Out of Scope**:

- CLI argument parsing (→ 0.1.1 Core Architecture, `main.py`)
- Runtime configuration hot-reload (not implemented)

### Bug Fix: validate() Reports Type-Invalid Values (PD-BUG-123, 2026-08-18)

- `validate()` performed type-dependent operations — `.upper()`, `<= 0`, iteration — directly on values that arrived unvalidated from YAML, so a well-formed config carrying a wrongly typed value **raised** (`AttributeError` / `TypeError`) instead of appearing in the issue list the method exists to return. `_from_dict`'s unguarded `set(value)` was the same defect one layer earlier: `monitored_extensions: 7` failed during *loading*, before `validate()` was reached.
- Fixed by type-guarding every checked field: new module helpers `_is_number()` (excludes `bool`, a subclass of `int` — `max_file_size_mb: true` previously passed validation silently as a size of 1), `_is_string_collection()` (excludes a bare `str` — `monitored_extensions: ".md"` previously coerced to `{'.', 'm', 'd'}`, three nonsense extensions) and `_wrong_type()` for the issue text. `_from_dict` now stores a wrongly typed value as authored rather than coercing, so `validate()` can name the key.
- **Coverage widened beyond the reported field**: all 5 `Set[str]` fields are type-checked (`monitored_extensions`, `ignored_directories`, `validation_extensions`, `validation_extra_ignored_dirs`, `validation_ignored_patterns`), not just the reported one. Loader tolerance without matching validation coverage would have traded a loud load-time failure for a later runtime one on the other four.
- **Second site, found during verification**: `main._apply_logging_config` runs *before* `config.validate()`, so `LogLevel(config.log_level)` raised `ValueError` and pre-empted the very report that names the key. Guarding `validate()` alone left the bug's own headline field (`log_level: 5`) still dying with a raw traceback at daemon startup. The helper now falls back to `LogLevel.INFO` so logging comes up and `validate()` can emit `config_issue`; the value is still fatal and `main()` still exits 1.
- **Downstream**: the Control Panel's CR-3 defensive handler (`config_edit.save_config`) no longer fires for these values — they now travel the normal `issues` path and the operator gets the validator's message naming the key instead of a wrapped `TypeError`. The handler stays (a pane must survive anything an external module throws) and its coverage was re-pointed to a forced-raise test rather than deleted.
- 21 regression tests written failing-first (17 red / 4 controls green pre-fix) plus 12 for the `main.py` half, mutation-verified. Full suite 1379 passed / 3 skipped / 4 xfailed. Manual validation `test/bug-validation/PD-BUG-123_config_validate_reports_type_errors_validation.py` — 19 checks including real daemon startup.

### Bug Fix: Numeric Validation Derives From the Schema (PD-BUG-127, 2026-08-19)

- Sibling of PD-BUG-123, filed at its closure and deliberately scoped out of that fix. `validate()` iterated a **hardcoded list of five** numeric field names while the dataclass declared **seven**, so `log_file_max_size_mb` and `log_file_backup_count` were never type-checked. Both are consumed by `main._apply_logging_config` *before* `validate()` runs, so nothing checked them at any point on the startup path.
- Three measured outcomes: `log_file_max_size_mb: big` raised `TypeError` in the `RotatingFileHandler` constructor and reached the operator as a generic `fatal_error` naming no key; `log_file_max_size_mb: true` was silently accepted as 1 MB (the `bool`-is-a-subclass-of-`int` trap `_is_number` exists for, on a field that never reached it); `log_file_backup_count: x` let the daemon **start** and then broke the first rollover inside the stdlib `emit` handler that swallows it — the triggering record lost, rotated logs never pruned, log directory growing without bound. A fourth variant found while designing the fix: `3.5` (and `3.0`) fail at the `backups[...]` slice, so this field needs a strict `int`, not merely a number.
- **Root cause fixed rather than the instance**: both hardcoded lists are gone. New `_schema_fields()` helper derives coverage from `dataclasses.fields` + `get_type_hints`, exactly as `_from_dict` already did, so a numeric or `Set[str]` field added to the schema cannot be left silently unvalidated. The type hint also carries the rule — an `int`-declared field requires a real `int`; `float`-declared fields still accept either. `_NUMERIC_MINIMUMS` declares the one field whose bound differs: `log_file_backup_count: 0` is a real setting meaning "rotate but never prune".
- **Second site, same pattern as PD-BUG-123**: `_apply_logging_config` now degrades each unusable rotation value to the schema default via `is_usable()` / `schema_default()` — one rule source shared with `validate()`, so the value logging starts with and the value the operator is told about can never disagree. Not a silent fallback: `validate()` still reports the key and `main()` still exits 1.
- **TD275 closed with this fix** — it recorded the same hardcoding on the `Set[str]` side, and its stated invariant is now mechanically enforced by a test that derives the field list from the dataclass independently of the production helper.
- Message wording for previously covered fields is unchanged (the PD-BUG-123 suite pins several byte-identically); the one operator-visible behavior change is that an `int`-declared field now rejects a fractional value, documented in the Configuration Guide's Troubleshooting section.
- 31 regression tests written failing-first (13 red pre-fix across the two files, the rest controls/drift guards) and mutation-verified. Full unit suite 1415 passed / 3 skipped / 3 xfailed. Manual validation `test/bug-validation/PD-BUG-127_rotation_config_validation_coverage_validation.py` — 18 checks including two real daemon startups and a before/after demonstration of the unpruned-log-growth consequence.

### Bug Fix: The Deferred Diagnosis Now Reaches Every Caller (PD-BUG-128, 2026-08-19)

- Third instance of the PD-BUG-123 / PD-BUG-127 pattern, and the first on the **caller** side. `_apply_logging_config` degrades an unusable value to the schema default and defers naming the offending key to `config.validate()`. That deferral was documented in three code comments and enforced nowhere, so it held only for callers that remembered it: `main()`'s daemon branch ran both halves, its `--validate` branch ran the first and never the second.
- **Measured, both halves**: `--validate` with `log_file_max_size_mb: big` and `log_file_backup_count: x` exited 0 with a clean report naming neither key, while the daemon with the identical config named both and exited 1.
- **Impact was wider than the report stated** — found during triage, not from the report. The missing call gates *every* key `validate()` checks, not just the two logging fields: `validation_extensions` given as a bare string (a real typo shape that `validate()` does catch) made the scan match `Path.suffix` against the characters of that string, examine nothing, and report "No broken links found" at exit 0 on a tree whose link was genuinely broken. A control run without the config exited 1 on the same tree. That false-clean is why the bug was re-prioritized Low to Medium at triage.
- **Root cause fixed rather than the instance**: new `_configure_logging_and_validate(args, config)` runs both halves and exits 1 with each offending key named; both branches call it and the daemon branch's inlined duplicate is gone. A caller can no longer take the fallback without the diagnosis — the pairing is structural rather than a comment.
- **Exit 1, not a new code**: the daemon already exits 1 on config issues, and the bug's own `AC` dimension is about the two call sites diverging — inventing a second convention on one path would widen exactly that gap. Nothing branches on the value today (the validate launcher passes `$LASTEXITCODE` through; the documented CI idiom is `||`). Warn-and-continue was rejected outright: it leaves exit 0 intact, so the false-clean survives for every automated caller.
- 8 regression tests written failing-first (5 red / 3 controls green pre-fix) driving `main.main()` end to end rather than the helper, since the defect is in the wiring between the halves. Mutation-verified: reverting only the validate-branch call turns exactly those 5 red and leaves the 3 controls green. Full suite 1432 passed / 3 skipped / 3 xfailed. Manual validation test skipped per the documented criterion — the automated tests drive the real CLI path end to end.
- One harness correction worth recording: a `log_level` case initially passed post-fix for the wrong reason, because `load_config` rewrites `config.log_level` to ERROR under `--quiet` (CLI-beats-config, by design) so the bad value never reached validation. Moved to its own non-quiet test rather than deleted, so the third field sharing this fallback shape stays covered.
- Docs updated: exit-code table in the link-validation handbook and the one-line summary in the capabilities reference now say `1` also means "configuration invalid"; the WF-006 configuration-change and WF-009 link-health-audit integration narratives were corrected for the new helper and the pre-scan exit. WF-009's E2E group (TE-E2G-013, 4 entries) flagged for re-execution; the 0.1.3-keyed cascade was deliberately not used, as it would have flagged 12 entries across four workflows the change does not touch.
- **Not fixed here**: PD-BUG-129, filed during this triage — `validate()` applies its should-start-with-a-dot check only to `monitored_extensions`, so a dotless `validation_extensions` still yields a false-clean and is untouched by this fix.

### Bug Fix: The Dot Check Derives From the Schema Too (PD-BUG-129, 2026-08-19)

- Fourth instance of the family and the **second on the callee side**: the leading-dot check named `monitored_extensions` literally while three schema fields hold extensions, so `validation_extensions` and `parser_type_extensions` escaped it entirely. It sits one check *below* the numeric loop PD-BUG-127 converted to schema derivation — the same file, the same function, the same defect, left behind by that fix.
- Both escapes fail the same silent way: by matching nothing against a `splitext` suffix that always carries its dot. Measured on a one-file tree — a dotless `validation_extensions` made `--validate` report `Files scanned: 0` and "No broken links found" at **exit 0**, where the identical tree exits 1 with no config. A dotless `parser_type_extensions` value is compared in `database.py` against a `splitext` result and silently filters every extensionless Python/Dart import reference out of lookups; being a `Dict`, that field escaped even the string-collection type check.
- **Root cause fixed rather than the instance**: `_extension_fields()` derives the set from `dataclasses.fields` by the `_extensions` name suffix all three already follow, and `_extension_issues()` handles both declared shapes (`Set[str]` entries, `Dict[str, str]` values). An extension field added later is checked without being listed.
- **Message wording changed, deliberately**: with three fields checked, `Extension 'md' should start with a dot` no longer told the operator which key was wrong — and that is the whole point of the bug (`OB`). Issues now read `validation_extensions entry 'md' should start with a dot`. The two automated assertions match on a substring and were unaffected; the one exact-match expectation in the PD-BUG-123 manual validation script was updated, and that script re-run green.
- **A second silent no-match folded in at the human partner's request** — the mirror image of the dotless one. `should_monitor_file` lowercased only the *file* suffix, leaving the case-insensitive matching the README documents half implemented: a `.MD` **file** already matched a `.md` entry, while a `.MD` **entry** matched nothing at all. Both sides are now normalized, with the direct lookup first so an all-lowercase config keeps its O(1) hit. Case is deliberately *not* a validation issue — `.MD` is a working entry, not a mistake; only the dot is enforced.
- **Sibling site found by the Step 20 sweep**: `_handle_directory_moved` tests `file_ext in self.monitored_extensions` directly instead of going through `should_monitor_file`, so it carried the identical asymmetry on the directory-move path. Fixed by normalizing once where the handler stores the set — which `add_extension` already assumed, since it lowercases what it adds. Cleared as unaffected: `parser.py`'s routing keys are hardcoded lowercase literals with no config involvement.
- **Composes with PD-BUG-128**, whose fix landed in a parallel session mid-work: this defect alone would have stayed invisible on the `--validate` path, since nothing there called `validate()`. Re-measured after both: the dotless config exits 1 naming the key. The uppercase half was never gated on it — it was silently broken on its own and now finds the broken link.

The coverage test derives the field set from the dataclass **independently of the production helper**, per the precedent PD-BUG-127 set, with a named floor list of the three known fields so the derivation itself is falsifiable. Full suite 1463 passed / 3 skipped / 3 xfailed.

### Bug Fix: merge() Honours Explicit Intent, Not a Default Comparison (PD-BUG-143, 2026-08-27)

- **A different family from PD-BUG-123 / 127 / 128 / 129.** Those four are all one root cause — `validate()` iterating a hardcoded field list where the schema declares more. This one is in `merge()`, and the mechanism is a *conflation*: with no record of which fields were set, `merge()` inferred it from `value != default`. `from_env()` builds a full `LinkWatcherConfig()` and mutates only the fields whose env var is present, so by the time `merge()` saw it, "set to the default" and "never set" were byte-identical. The env value was discarded and the config file won, contradicting the precedence documented in FDD 3.1.1-BR-6 and in `settings.py`'s own class docstring. Silent: no warning, no log record.
- **Booleans made it structural, not a corner case.** A boolean has only two values — the default and not-the-default — so whenever a config file set the meaningful one, the environment's counter-value *was* the default. For all **17 boolean fields (44% of the 39-field schema)** the environment could never reverse a file setting in either direction. `dry_run_mode` had no escape at all: `--dry-run` only sets True and there is no `--no-dry-run`, so a file that enabled dry run could not be disabled from anywhere. Demonstrated against the shipped `config-examples/production-config.yaml`, where three env overrides were discarded while `from_env()` alone read all three correctly — locating the loss at `merge`, not at parsing.
- **Fix**: `__post_init__` creates an empty explicit-field record and `__setattr__` adds to it, so every post-construction assignment is recorded — which is exactly how `_from_dict()` and `from_env()` build their instances, so **both layers were captured with no change to either constructor**. `merge()` overrides on membership, falling back to the historical `!= default` rule when `other` recorded nothing, which leaves programmatic `LinkWatcherConfig(field=value)` callers unaffected. The record deliberately is not a dataclass field, so `dataclasses.fields()`-derived coverage (the validation helpers, the schema-drift test) is untouched; `to_dict()` and both `merge` loops skip `_`-prefixed keys so it can never be written into a user's saved config.
- **Bound established**: the CLI layer is unaffected — `main.load_config` assigns CLI overrides directly, never through `merge()` — so env-over-file was the sole live surface. The Step 20 sweep confirmed `merge()` is the only site in the codebase inferring explicit intent from a default comparison (`_usable_or_default` is the unrelated PD-BUG-127 fallback).
- **Behavior-preserving for file-only configuration**: a file value equal to the default was previously dropped as a no-op against a defaults base and is now applied — the same value either way.
- 13 regression tests added to `test_config.py`; 6 written failing-first and confirmed red pre-fix for the right reason, with 7 controls green pre-fix. The breadth test derives the boolean field set from the dataclass, with a named floor list so the derivation itself is falsifiable, per the precedent PD-BUG-127 and PD-BUG-129 set. Full suite 1623 passed / 3 skipped / 3 xfailed. Verified end to end through `main.load_config`, the real daemon entry path.
- **Documentation**: PD-INT-009 documented the defect as "a semantic subtlety of the merge algorithm" and was corrected; the Configuration Guide's boolean type row now states how to set a boolean false; TE-TSP-037 gained unit and integration scenarios. No FDD/TDD (Tier 1 feature). **Completed after code review (2026-08-27)**: the review found the Configuration Guide's *Environment variable ignored* troubleshooting entry still claiming that boolean values must be `true`, `1`, `yes` or `on` — contradicting the type table corrected by this same fix, and preserving the dead end triage had folded in as documentation item (e): a user disabling a boolean from the environment was told those four were the only valid values. That sentence now states both directions. Sweep confirmed no other site in `doc/` or `README.md` carries the claim; the remaining `LINKWATCHER_DRY_RUN_MODE=true` mentions are enable-side examples and are correct.
- **Sequencing note**: fixed ahead of PD-BUG-142, whose approved fix has the daemon publish its *effective* `move_detect_delay` for the Control Panel to read — with this defect unfixed, that published value would itself have been wrong for the env-set-to-default case.

## 8. Design Decisions

### Decision 1: Multi-Source Configuration with Precedence

**Date**: Pre-framework (discovered in code)
**Context**: Different deployment environments need different configuration methods — developers prefer config files, CI uses environment variables, quick testing uses CLI flags.

**Decision Made**: Support 4 sources with strict precedence: CLI > environment variables > config file > defaults

**Rationale**: Follows the standard configuration cascade pattern used by most Unix tools. CLI flags are always highest priority for quick overrides; defaults ensure the tool always works out-of-the-box.

**Implications**:

- Users can mix sources freely — e.g., config file for base settings, env var to override log level in CI
- `validate()` runs after merging all sources, catching conflicts regardless of origin

---

### Decision 2: Dataclass-Based Configuration

**Date**: Pre-framework (discovered in code)
**Context**: Configuration needs type safety, default values, and easy serialization.

**Decision Made**: `LinkWatcherConfig` as a Python `@dataclass` with typed fields

**Rationale**: Dataclass provides `__init__`, `__repr__`, type hints, and default values with no boilerplate. IDE autocompletion works naturally. Validation is a method on the class itself.

---

### Decision 3: Environment Presets

**Date**: Pre-framework (discovered in code)

**Rationale**: Reduces configuration burden for common cases. Users can start with a preset and override specific values rather than configuring every option individually.
